# PhenX import for the eSheet builder

The first milestone is a builder demo in which a developer finds one real PhenX questionnaire, previews it, imports it, and sees the right follow-up questions appear. Its source IDs and attribution must survive an edit, export, and reimport. Phases 1 and 2 each produce a reviewable PR in eSheet. Revisit the remaining phases after each demo. [Feature request · eSheet #263](https://github.com/mieweb/eSheet/issues/263)

## Where Codify fits

Codify supports medical code lookup. Its pipeline extracts code rows from WebChart’s `MedicalCodify_search` table in MariaDB. It builds a SQLite full-text search database for server-side lookup and separate `.mcdx` search files for browsers. A lookup can return a code, label, and coding system. A PhenX import also needs the ordered questions, answer codes, skip rules, revision, and source credits. Those come from the official instrument and cross-references. [Codify architecture](https://github.com/mieweb/ui/blob/0fef0ed216593e44986a08254e7af00d26d0cc0d/src/components/CodeLookup/README.md) · [PhenX downloads](https://www.phenxtoolkit.org/resources/download)

| Decision                          | Starting recommendation                                                                                                                                                                                                                    | Evidence that could change it                                                                                                                                                                               |
| --------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Use the Codify database?          | **No database dependency for import.** Use the mappings PhenX publishes. A host with Codify can later display a label for an exact LOINC code. A missing match leaves the original code intact.                                            | A consumer needs server-side PhenX lookup and a maintainer agrees to own its data and updates.                                                                                                              |
| Use Codify to distribute lookups? | **Start with an eSheet-hosted, versioned index.** Test the existing `@esheet/catalog` compiler, which can build a dedicated PhenX search file from CSV. Selecting a search hit resolves its ID and release to a separate protocol payload. | A second consumer needs the same index, a Codify maintainer can publish and roll it back, and the data can be redistributed to that audience. Compare the same lookup cases on both hosts before switching. |

Using the same search file format leaves the hosting decision open. The generic eSheet worker verifies the file digest and keeps the loaded index in memory. A successful search does not guarantee the protocol payload is available offline. [Catalog compiler](https://github.com/mieweb/eSheet/blob/8e7d259cb7ed1a518e00da6b545f0bf3486445c5/packages/catalog/src/compiler.ts) · [Catalog worker](https://github.com/mieweb/eSheet/blob/8e7d259cb7ed1a518e00da6b545f0bf3486445c5/packages/catalog/src/runtime/catalog-worker.ts)

## Phase 1 — Prove the source data and lookup

- [ ] **Collect one pilot.** Start with Family History of Heart Attack (`040101`). Download the REDCap ZIP and the protocol and variable cross-reference spreadsheets. Record the official URLs, DOI, source release when available, retrieval date, and SHA-256 of each input. Read the instrument’s availability and original source terms before committing or hosting any questionnaire text. If redistribution is unclear, keep the official files local and commit a synthetic fixture plus reproduction instructions. [Pilot protocol](https://www.phenxtoolkit.org/protocols/view/40101) · [REDCap ZIP](https://www.phenxtoolkit.org/toolkit_content/redcap_zip/PX040101.zip) · [Downloads and license](https://www.phenxtoolkit.org/resources/download) · [PhenX FAQ](https://www.phenxtoolkit.org/help/faq)
- [ ] **Account for every row.** Open `instrument.csv` inside the ZIP. Use the data dictionary CSV for variable detail and consult the RTF or worksheet when a skip rule is ambiguous. Record any disagreement for review. Make a table with one row per REDCap field showing its name, type, answer codes, required flag, branch, matching PhenX variable ID, and proposed eSheet treatment. The sampled instrument has 16 rows, including a REDCap record ID, instructions, and a helper named `var1`. Explain any omission. Preserve a helper’s REDCap name when it has no published variable ID.
- [ ] **Check the joins by hand.** The spreadsheet uses `40101` and the DOI uses `040101`. Retain the source spellings and document the join. Expect LOINC `62390-0` and HPO `HP:0001658` on the **protocol** and `PX040101020100` on the mother’s question. Record missing or ambiguous matches explicitly. The variable cross-reference includes dbGaP mappings, so inspect its headers before treating a column as a terminology code. [Pilot standards and variables](https://www.phenxtoolkit.org/protocols/view/40101) · [PhenX interoperability](https://www.phenxtoolkit.org/about/interoperability)
- [ ] **Try discovery with a small index.** Make a local manifest with one entry per protocol per release. Include ID, title, domains, collections, keywords, official URL, import availability, and a payload reference and digest for importable entries. Add Birthplace (`010201`) as a second metadata entry. Test exact ID with and without the leading zero, title, keyword, domain, collection, and an empty result. Compile the same rows with `@esheet/catalog/compiler` using `idColumn` and explicit `searchColumns`. Compare the results with the manifest, including membership in two collections. Keep collection arrays in the manifest if a flat search attribute loses a match. [Birthplace](https://www.phenxtoolkit.org/protocols/view/10201) · [Catalog mapping options](https://github.com/mieweb/eSheet/blob/8e7d259cb7ed1a518e00da6b545f0bf3486445c5/packages/catalog/src/index.ts)
- [ ] **Phase 1 review.** Hand over the input manifest, row table, lookup cases and results, and one command that reproduces them from pinned inputs. The reviewer should be able to trace a search hit to the correct ZIP and each expected code to its source. Record which index to use in Phase 2 and which rows or rights questions still need a decision.

## Phase 2 — Import one whole protocol in the builder

- [ ] **Build the adapter first.** In `packages/adapters/src/phenx/`, add a converter that takes the Phase 1 instrument and source metadata and returns a candidate `FormDefinition` plus diagnostics. Keep downloading and form mutations outside it. Map REDCap text, descriptive, and radio rows to eSheet’s `text`, `display`, and `radio` fields. Preserve order, answer codes, and required flags. Use deterministic field IDs and validate the result with `formDefinitionSchema.safeParse`. Report duplicate IDs, unsupported types, and unsupported rules with the offending field name. [Existing adapter](https://github.com/mieweb/eSheet/blob/8e7d259cb7ed1a518e00da6b545f0bf3486445c5/packages/adapters/src/fhir/fhir-adapter.ts) · [eSheet schema](https://github.com/mieweb/eSheet/blob/8e7d259cb7ed1a518e00da6b545f0bf3486445c5/packages/core/src/lib/types.ts)
- [ ] **Prove one branch in the renderer.** The ZIP uses `[var1] = '2'` on 12 relative questions. In that selector, `2` means Yes. Translate it to an eSheet visibility rule referencing the controlling field ID and matching option ID. Test unanswered → Yes → No → Don’t Know. Expect 0 → 12 → 0 → 0 visible follow-ups. Block a complete import when a required branch cannot be represented or its target is missing. Show the source expression in the diagnostic. [Condition evaluator](https://github.com/mieweb/eSheet/blob/8e7d259cb7ed1a518e00da6b545f0bf3486445c5/packages/core/src/lib/logic/conditions.ts)
- [ ] **Keep provenance with the form.** Use a typed, versioned `_sourceData.phenx` entry for the protocol ID, source revision or digest, URL, DOI, attribution, and protocol-level mappings. On each applicable field, retain the REDCap name, source variable ID, and any explicit variable-level mappings. Keep other source metadata when editing. Include the original instrument credit, license link, and a note that eSheet converted the instrument. Show the attribution below in the preview and on the imported form.

  > The Web-based PhenX Toolkit currently receives funding from the National Institutes of Health; official current and archived versions of the PhenX Toolkit are available at www.phenxtoolkit.org.

- [ ] **Wire the builder demo.** Add “Import from PhenX” beside the existing builder import action. Use the Phase 1 index. Preview the protocol, fields, source, and warnings. For the pilot, import into a new form or an empty builder. A canceled preview, failed download, digest mismatch, or blocked mapping must leave the author’s existing form and responses intact. Only call `loadDefinition` after validation and user confirmation. [Builder import and export](https://github.com/mieweb/eSheet/blob/8e7d259cb7ed1a518e00da6b545f0bf3486445c5/packages/builder/src/lib/components/BuilderHeader.tsx) · [Form store](https://github.com/mieweb/eSheet/blob/8e7d259cb7ed1a518e00da6b545f0bf3486445c5/packages/core/src/lib/stores/form-store.ts)
- [ ] **Phase 2 review.** With Codify unavailable, find `040101` by title and ID, preview, import, and run the four-answer test. Edit the form title, export native YAML and JSON, and reopen each in the builder. Assert the same variable IDs, protocol codes, attribution, and skip behavior. From the eSheet root, run `pnpm build`, the affected package tests (e.g. `pnpm --filter @esheet/adapters test --run` and `pnpm --filter @esheet/builder test --run`), and `pnpm dev:demo` for the walkthrough. Attach the results and update the remaining phases with what failed or required manual review.

## Later phases — revise after the pilot

- [ ] **Phase 3 · Selective import and broader coverage.** Preview variable selection and include or explain dependencies. Handle field ID collisions when adding to an existing form. Show a PhenX source badge or panel. Exercise demographics, cardiovascular, mental health, and environmental exposure protocols and document unsupported field types and logic.
- [ ] **Phase 4 · Decide how to publish lookups.** Compare eSheet hosting with an optional dedicated Codify distribution using the same release and lookup cases. Record download size, load time, filter parity, reuse permissions, and who owns refresh and rollback. Publish the index and permitted payloads under immutable names before switching the manifest. Test a stale index and a missing payload.
- [ ] **Phase 5 · Document and release.** Publish a builder guide covering search, preview, full and selective import, attribution, and mapping limits. Verify representative protocols against the ticket and record deferred cases. Bidirectional sync, new LOINC codes, and added clinical scoring are outside this release.
